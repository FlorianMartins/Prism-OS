# Spec v0.6 — Customization

> Status: implemented (2026-10-04): themes, export/import, tiling window manager.
> Follows `v0.5-privacy.md`.

## 1. Colour themes (`prism-core/src/theme.rs`)

- 8 presets adapted from published palettes of free projects — **Prism** (default
  cyan), **Nord**, **Dracula**, **Catppuccin Mocha**, **Gruvbox**, **Tokyo Night**, a
  **red gaming** theme and **Clair** (light, Solarized) — plus an optional custom accent.
- A palette gives each role a colour: background, panel, card, raised card, border,
  text, secondary text, accent, success, warning, error. The dimmed accent (selection,
  active window) is derived by mixing the accent into the background, so a custom
  accent never needs a second colour.
- **Readability is tested**, not assumed (test `every_preset_is_readable`, WCAG 2.x
  contrast): text ≥ 7:1 and secondary text ≥ 4.5:1 on background, cards and raised
  cards; accent ≥ 3:1 on the background; text on the accent ≥ 4.5:1 (the text colour on
  accent buttons is chosen per theme, dark or light); text on the selection ≥ 4.5:1.
  The first run of this test caught five presets below the thresholds; their secondary
  text or raised-card colours were adjusted by the smallest amount that passes.
- Stored in `bar.json` (`theme`), read by both programs: the Prism Bar (GDI) reloads it
  with the rest of its settings within a second; the app (egui) switches its visuals
  (dark or light base) immediately. The bar preview in the app uses the chosen palette.
- In the app the palette is per UI thread (the screenshot tests render pages in
  parallel; a global palette made one test paint another test's theme).

## 2. Export / import (`prism-core/src/backup.rs`)

- One JSON file, `format: 1`: bar settings (theme included), the user's
  `config.toml` (if any), appearance values, the debloat levels and the privacy level
  that are **fully** applied (detected from the system state, not from the journals).
- Import validates first: format version, `config.toml` parsed, appearance settings
  unknown to this version or values not offered are dropped with a warning, bar
  settings clamped. Then it writes the bar settings, keeps the previous `config.toml`
  as `.bak`, and applies appearance, debloat and privacy through their own modules and
  journals — every restore command still works. Import never removes a level.
- Journals are never exported: they record the original state of one machine.
- Accepts a UTF-8 byte-order mark (files edited with PowerShell 5 or Notepad).

## 4. Tiling window manager

> Status: implemented (2026-10-04).

- **Layouts** (`prism-core/src/tiling.rs`, pure geometry, 7 tests): *master + stack*
  (main window on the left, adjustable 20–80 %), *columns*, *spiral* (each split along
  the longest side) and *monocle*; configurable gap between windows and around the
  screen edge. Tests check that tiles cover the work area exactly without overlapping,
  for 1 to 7 windows.
- **Applied by the Prism Bar** (`prism-win/src/tiler.rs`), per screen, inside the work
  area left by the taskbars, with `SetWindowPos` (documented API, as komorebi or
  FancyZones use). The visible frame is placed exactly by compensating the invisible
  borders of Windows 10/11.
- **Which windows**: normal resizable top-level windows only — never a game, an
  anti-cheat or a protected process (File Explorer windows excepted: ordinary windows,
  the process itself stays protected from Game Mode), never fullscreen, dialogs,
  minimized or maximized windows, nor programs on the user's exclusion list. Nothing
  moves while Game Mode is active.
- **Windows that cannot fit** (minimum size larger than their tile, e.g. Discord or
  Calculator on a 1280×800 screen) are left floating at their original place, one at a
  time — the one overflowing most — and the layout is recomputed; they are retried
  when the set of windows changes. The check happens one pass later: Store apps apply
  a new size asynchronously, so reading it immediately gave stale sizes.
- **Order and moves**: windows keep their place in the order; a new window goes to the
  end; dropping a window on another tile swaps them (the drag jelly flows into the new
  tile). Windows moved by the tiler do not trigger the maximize/snap animation.
- **Undo**: each window's original frame is recorded (`%ProgramData%\Prism\tuiles.json`:
  window, process, frame) and given back when tiling is turned off or the bar stops;
  if the bar was killed, the next start gives them back. A floating window keeps its
  recorded original frame.
- **Shortcuts** (`RegisterHotKey`): **Win+Ctrl+Alt** + W on/off, Space next layout,
  Enter active window as main, Left/Right previous/next window, Up/Down main width,
  F float/tile the active window. Probed in the VM: Windows 11 26H2 already takes
  Win+Alt+W, F, Y and the arrows (and the Game Bar uses Win+Alt+B, G, K, M, R, T),
  while every Win+Ctrl+Alt combination was free; Ctrl+Alt alone is AltGr on European
  keyboards.

### Verified in the VM (two 1280×800 screens)

| Check | Result |
|---|---|
| Explorer + Calculator + Discord on screen 1, Notepad on screen 2, *master + stack* | Explorer main on the left, Calculator in the stack, Discord (too large) floating; Notepad fills screen 2 |
| Win+Ctrl+Alt+Space | layout cycles (columns → spiral), saved to `bar.json` |
| *Spiral* with two windows | halves with 8 px gaps |
| Turn off | every window back to its exact original frame |
| Bar killed while tiling, restarted, then tiling turned off | Calculator back to 900,150 340×520 and Explorer to its original frame |

Bugs found in the VM and fixed: File Explorer was excluded (it is in the protected
process list, which is meant for Game Mode); Discord was moved every second because it
refused a tile smaller than its minimum size; two windows were floated at once when
floating one was enough; Store apps' delayed resize was read too early; a window that
went floating lost its original frame.
