# Spec v0.1 — Game Mode, RAM policy, profiles, cyber tools

> Status: being implemented (2026-10-04).
> Read together with `docs/ARCHITECTURE.md` and `docs/anticheat-rules.md`.

## 1. What v0.1 delivers

A command-line engine (`prism.exe`) that runs on the user's Windows:

1. **Automatic Game Mode**: detects when a game is launched, pushes the background into
   the back seat, frees the RAM it holds without using it, then restores everything
   exactly as it was when the game closes.
2. **On-demand RAM cleaning** (`prism ram clean`).
3. **Usage profiles**: Gaming, Cyber, Balanced.
4. **Cyber tool catalog**, installable on demand (winget + Kali under WSL), with
   detection of tools that interfere with anti-cheats.

The graphical interface (launcher, dashboard, themes) was planned for v0.2 and will
drive this engine (it was eventually delivered in v0.3, see `docs/ARCHITECTURE.md`).

## 2. Process classification

Each process in the user's session receives **one** class, in this order:

| Order | Class | Rule | What is done to it |
|---|---|---|---|
| 1 | `Protected` | Prism itself, another session (services), protected list (system, anti-cheats, antivirus, audio, shell) | **nothing, ever** |
| 2 | `Conflict` | process of a tool flagged as interfering with anti-cheats (debugger…) | nothing, but reported |
| 3 | `Game` | executable under a game library root (Steam, Epic, GOG, Xbox, Riot, Battle.net, EA, Ubisoft) or named in `games`; excluding helper processes (`game_helpers`) | **nothing** — the game is never touched |
| 4 | `Companion` | Discord, OBS, Steam, overlays, GPU tools… (`companions`) | nothing: they are useful during gameplay (voice, capture) |
| 5 | `Background` | everything else | pushed back (§3) |

A process's identity is **(PID, creation time)**. A PID reused by another process is
therefore never mistaken for the old one, neither when acting nor when restoring.

## 3. What Game Mode does to the background

Everything goes through documented Windows APIs, called from outside the game:

| Lever | API | Effect | Restored? |
|---|---|---|---|
| CPU priority | `SetPriorityClass` | `BELOW_NORMAL`: the game goes first | yes, original value |
| EcoQoS | `SetProcessInformation(ProcessPowerThrottling)` | Windows places the process on efficient cores and lowers its frequency | yes |
| Memory priority | `SetProcessInformation(ProcessMemoryPriority)` | its pages will be reclaimed **first** | yes, original value |
| Working set trimming | `EmptyWorkingSet` | its RAM leaves active memory | no (comes back on use) |
| Flush + purge of the priority-0 cache | `NtSetSystemInformation(MemoryFlushModifiedList, then MemoryPurgeLowPriorityStandbyList)` | makes that RAM actually free | no |
| Power plan | `PowerSetActiveScheme` | high performance | yes, original plan |
| WSL | `wsl --shutdown` | returns the Linux VM's RAM (`vmmem`) | no (restarted on demand) |

New processes launched during a session: handled on the next pass (every 2 s).

## 4. RAM policy — why this exact order

Point raised by Florian: after a long office-work session, Word keeps RAM even though it
is no longer in use, and we want to give everything to the game. This is true for a
**program that is still open but idle**: its working set stays reserved, and Windows only
reclaims it when the game runs short, under pressure, which causes stutters. It is better
to do it **beforehand**, when the game starts.

A brute-force cleanup has two flaws:
- emptying **everyone's** working set, the game's included, forces it to reload everything;
- emptying the **whole** file cache also throws away the data the game has just read
  (textures, levels), which lengthens loading times.

Hence Prism's sequence, applied only to `Background` processes:

1. **memory priority → low**: if the game runs short of RAM before Prism acts,
   Windows removes these processes' pages first (and not the game's);
2. **trimming** (`EmptyWorkingSet`): their pages leave active memory;
3. **flushing the modified list** (`MemoryFlushModifiedList`): the trimmed private pages
   are written to the page file and move into the **priority-0** cache;
4. **purging only the priority-0 cache** (`MemoryPurgeLowPriorityStandbyList`), if free
   RAM is below the profile's threshold.

Result: Word's RAM is actually free for the game, and the cache of the game's files
(priority 5) is intact. `prism ram clean --deep` purges the whole cache, on explicit
request only.

### 4.1 Measurements (Windows 11 Enterprise 26H2 VM, 12 GB, 2026-10-04)

Bench: `crates/prism-win/examples/memlab.rs`, scripts in the test VM.

| Experiment | Result |
|---|---|
| Idle 3 GB program, trimmed, **without** flushing the modified list, immediate purge | pages still in the modified list (3.1 GB): **nothing freed**. This is what the 1st CI run showed ("RAM libérée : 0 Mo" — "RAM freed: 0 MB") |
| Same thing, 20 s later | the pages reach the priority-0 cache (3,071 MB); the purge frees **3 GB**; the normal 3 GB cache ("game data") stays intact |
| Trim + forced flush + purge, memory priority 1, 2 or 5 | **2 GB freed in all three cases**: for private memory, memory priority changes nothing for the purge, only the flush matters |
| Real `prism ram clean`, idle 3 GB program | free RAM **44% → 68%** (2.9 GB), memory priorities reset to their original values |

Good to know:
- `MemoryPurgeLowPriorityStandbyList` only empties **priority 0**; Windows offers
  nothing between "priority 0" and "the whole cache";
- *file* pages (program code, mapped files) keep their read priority and are not freed
  by the low purge; Windows reclaims them on demand, after lower-priority pages.

Accepted cost: the flush writes modified pages to the page file. This happens once, when
the game starts, not in the middle of a session.

## 5. Profiles

| Profile | Auto Game Mode | Background | RAM | Power | WSL |
|---|---|---|---|---|---|
| **Gaming** | yes | `BELOW_NORMAL` + EcoQoS + low memory priority | trim + low-priority purge below 25% free | high performance | stopped when a game starts |
| **Balanced** | yes | `BELOW_NORMAL` + EcoQoS | nothing | unchanged | unchanged |
| **Cyber** | no | nothing | nothing | unchanged | free (Kali) |

The active profile is stored in `%ProgramData%\Prism\state.json`.

## 6. Cyber tools without performance loss

- Nothing is installed by default; packs are installed on demand (`prism tools`).
- Native Windows tools go through winget, with identifiers verified in
  `microsoft/winget-pkgs`. Linux tools (nmap, sqlmap, hashcat…) go through **Kali
  under WSL** (`OffSec.KaliLinux`), which consumes nothing while WSL is stopped.
- **Zero in-game cost**: no tool runs in the background, and the Gaming profile stops
  WSL when a game starts.
- **Anti-cheat conflicts**: each tool declares its processes. A debugger (x64dbg,
  Cutter) or a kernel-driver tool (Process Explorer) open during a game is reported:
  some anti-cheats refuse to start, or even ban. v0.1 warns without closing anything.

## 7. Crash recovery

Each reversible change is written to a **journal** (`%ProgramData%\Prism\journal.json`)
**before** moving on to the next one. If Prism is killed mid-session, the next start
reads the journal back and restores, checking the identity (PID + creation time) of each
process.

## 8. Tests

- `prism-core` (pure logic: classification, plan, journal, RAM policy, catalog):
  unit tests run on Linux with a simulated platform.
- `prism-win`: integration tests run by CI on a **real Windows**
  (`windows-latest`): child processes are launched, each lever is applied, the actual
  value is read back through the API, restored, and read back again.
- What CI does not prove: the FPS gain and compatibility with each anti-cheat.
  These two measurements are done on a real gaming PC, with a protocol published in
  `docs/measurements.md` (v0.2).
