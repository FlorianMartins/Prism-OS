# Spec v0.4 — Window effects

> Status: implemented (2026-10-04). Follows `v0.3-interface.md`.
> Request from the product owner: effects beyond Windows' own animations, as on
> Bazzite/KDE — modern deformations, jelly ("wobbly") windows, a genie/suction effect on
> minimize — and transparency configurable element by element (done in v0.3 §6b).

## 1. Constraint

On Linux, the compositor (KWin) is open and loads effect plugins. On Windows, the
Desktop Window Manager is closed and exposes no extension point for custom window
effects. Prism does **not** modify system components to get one: that is precisely what
anti-cheats watch for (rules 1, 3 and 5 of `anticheat-rules.md`).

## 2. Approach: Prism draws the effect over the real window

Everything runs in the Prism Bar process, with documented APIs only:

1. **Detect the transition** with accessibility events received out-of-context in
   Prism's own process (`SetWinEventHook`): foreground change, minimize start/end,
   window shown/hidden. Clicks on the bar's own window buttons are handled directly.
2. **Copy the window** with `PrintWindow(PW_RENDERFULLCONTENT)`, cropped to the visible
   frame (`DWMWA_EXTENDED_FRAME_BOUNDS`, without Windows 11's invisible borders). The
   copy is in memory only, never written to disk.
3. **Compute each frame in software** (`prism-core/src/fx.rs`, pure Rust, unit-tested
   and previewed as PNG frames on Linux) and show it in a click-through, non-activating
   layered overlay (`UpdateLayeredWindow`), paced on the compositor with `DwmFlush`.
4. **Hand back to Windows**: the real window changes state under the overlay. For an
   appearance (restore, open), it is kept invisible (layered, alpha 0) until the last
   frame, then its original style is put back.

Software rendering was chosen over a GPU stack: the bar runs all the time and must stay
light (19 MB with effects), and a frame costs under 2 ms on one core (§5).

## 3. Effects

| Effect | Description | Default use |
|---|---|---|
| Genie lamp | the window narrows and is sucked into its Prism Bar button; reversed on restore | minimize, restore |
| Jelly | spring-damped wobble with overshoot | open |
| Zoom and fade | scale + opacity | close |
| None | Windows' behaviour | — |

Each of minimize, restore, open and close takes any effect. Duration 120–900 ms,
deformation intensity 0–100 %. Enabling effects sets Windows' own minimize animation to
instant (a journaled Appearance setting) so the two do not overlap.

## 4. Safety and timing rules

- Never on a game (Game Mode classification + detected library folders), on a fullscreen
  window, on Prism's own windows, on owned/tool windows, on windows smaller than
  200×120, or while Game Mode is active.
- The overlay is click-through and never takes focus.
- **A late effect is worse than none**: an event older than 250 ms is skipped.
- An effect Prism triggered itself (bar click) is not animated again when Windows
  reports the same transition.
- The window is copied *before* the transition, so copying never delays the effect:
  when it gets focus, and again when the mouse button goes down on its bar button.
  A minimized window is never copied (Windows parks it off-screen as a 160×28 stub).
- Every animation is measured (latency to first frame, time per frame, dropped frames)
  into `%ProgramData%\Prism\fx-stats.json` (last 50); `prism fx stats` prints them and
  `prism fx demo` plays a measured sequence on the foreground window.

## 5. Measurements

Frame computation alone, release build, one core of the build server, 1280×720 window on
a 1920×1080 overlay (`cargo test --release -p prism-core fx_bench -- --ignored --nocapture`):

| Effect | Average | Worst |
|---|---|---|
| Genie | 1.4 ms | 4.5 ms |
| Jelly | 2.4 ms | 5.3 ms |
| Zoom | 2.3 ms | 3.1 ms |

On Windows (VM, software rendering): latency to first frame 2–6 ms, 1.4–2 ms per frame,
0 dropped frames. Details and the bugs these measurements found:
`docs/measurements.md` §6.

## 6. Not done yet

- **Jelly while dragging a window**: needs the window to be hidden and redrawn by Prism
  for the whole drag; only worth it if the latency stays invisible. Prototype first.
- **Glide on maximize / snap.**
- **Open effect** depends on how fast the new window draws its first content: it is
  played on whatever the window shows when it appears.
- Multi-monitor: effects follow the virtual screen, but the bar (genie target) is on the
  primary monitor only.
- Validation on physical hardware (integrated GPU, high refresh rates).
