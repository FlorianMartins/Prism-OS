# Spec v0.4 — Window effects

> Status: implemented (2026-10-04). Follows `v0.3-interface.md`.
> Request from the product owner: effects beyond Windows' own animations, as on
> Bazzite/KDE — modern deformations, jelly ("wobbly") windows, a genie/suction effect on
> minimize — and transparency configurable element by element (done in v0.3 §6b).

## 1. Constraint

On Linux, the compositor (KWin) is open and loads effect plugins. On Windows, the
Desktop Window Manager is closed and exposes no extension point for custom window
effects. Prism does **not** modify system components to get one: that is precisely what
anti-cheats watch for (rules 1, 3 and 5 of `anticheat-rules.md`).

## 2. Approach: Prism draws the effect over the real window

Everything runs in the Prism Bar process, with documented APIs only:

1. **Detect the transition** with accessibility events received out-of-context in
   Prism's own process (`SetWinEventHook`): foreground change, minimize start/end,
   window shown/hidden. Clicks on the bar's own window buttons are handled directly.
2. **Copy the window** with `PrintWindow(PW_RENDERFULLCONTENT)`, cropped to the visible
   frame (`DWMWA_EXTENDED_FRAME_BOUNDS`, without Windows 11's invisible borders). The
   copy is in memory only, never written to disk.
3. **Compute each frame in software** (`prism-core/src/fx.rs`, pure Rust, unit-tested
   and previewed as PNG frames on Linux) and show it in a click-through, non-activating
   layered overlay (`UpdateLayeredWindow`), paced on the compositor with `DwmFlush`.
4. **Hand back to Windows**: the real window changes state under the overlay. For an
   appearance (restore, open), it is kept invisible (layered, opacity 1/255) until the last
   frame, then its original style is put back.

Software rendering was chosen over a GPU stack: the bar runs all the time and must stay
light (19 MB with effects), and a frame costs under 2 ms on one core (§5).

## 3. Effects

| Effect | Description | Default use |
|---|---|---|
| Genie lamp | the window narrows and is sucked into its Prism Bar button; reversed on restore | minimize, restore |
| Jelly | spring-damped wobble with overshoot | open |
| Zoom and fade | scale + opacity | close |
| Squash (KDE "Squash") | linear shrink into the Prism Bar button, fading at the end | — |
| Fade | opacity only | — |
| 3D tilt (KDE "Glide") | pivots back around its bottom edge in perspective, fading | — |
| Fall apart (KDE "Fall Apart") | breaks into 24–64 px tiles that fly out, spin, fall and fade; reassembles when opening | — |
| None | Windows' behaviour | — |
| Jelly while dragging | spring grid that follows the moving window (§3b) | drag (on/off) |

Each of minimize, restore, open and close takes any effect (renderers in
`prism-core/src/fx_effects.rs`; a test checks that every closing effect starts as the
intact window, moves at mid-course and ends fully gone).

**Maximize / snap / back to normal size** has its own choice: Glide (the copy moves and
stretches from the old frame to the new one, eased), Jelly (same path, spring overshoot
and squash), Crossfade, or none. Detection: Windows has no maximize/snap event for other
apps' windows, so the bar subscribes to `EVENT_OBJECT_LOCATIONCHANGE` **for the
foreground app's process only** (re-subscribed when the foreground app changes; never
system-wide, which would wake the bar on every mouse move). A size change of more than
8 px that is not an interactive resize (`GUI_INMOVESIZE`) and less than 250 ms old is
animated from the last known frame, using the last copy if it has that frame's size. No
capture on the critical path: the real window, already at its new size, is hidden at
1/255 and its opacity follows `Morph::window_alpha` while the copy fades out; a fresh
copy is taken after the animation. A drop on a screen edge during a jelly drag goes
straight from the jelly to the snap animation, without showing the window in between. Duration 120–900 ms,
deformation intensity 0–100 %. Enabling effects sets Windows' own minimize animation to
instant (a journaled Appearance setting) so the two do not overlap.

## 3b. Jelly while dragging (`prism-core/src/wobbly.rs`)

- **Physics**: an 8×8 grid of points, each on a damped spring around its rest position
  on the window. When the window moves, each point keeps its screen position and its
  spring pulls it back, so far parts trail, overshoot when the window stops and settle.
  Points near the grabbed point are stiffer, and the deformation is weighted to zero
  there, so the point under the cursor never moves. Displacement is bounded; the
  integration step is capped at 2 ms, so a late frame cannot make it unstable.
  Intensity sets the softness (≈ 3 Hz far from the cursor at 70 %).
- **Rendering**: the copy is drawn on a 28×28 mesh of textured triangles; a frame costs
  3.1 ms on average for a 1280×720 window on one core of the build server
  (`cargo test --release -p prism-core wobbly_bench -- --ignored --nocapture`).
- **Windows side**: `EVENT_SYSTEM_MOVESIZESTART` starts it. A press on the window's
  borders (resizing) or a maximized window is skipped. The window is copied while still
  shown, then hidden; each frame reads its position (`DWMWA_EXTENDED_FRAME_BOUNDS`),
  advances the springs and redraws the overlay around it. The bar posts itself one
  message per frame, so its message loop keeps running during a drag.
- **End**: read at every frame from the window's thread (`GetGUIThreadInfo`,
  `GUI_INMOVESIZE`) — in the VM the end-of-move event sometimes never arrived. After
  release the jelly settles (≤ 1.5 s), then the real window reappears in place. A size
  change (resize, snap, maximize) hands the window back at once.
- **Hiding**: opacity 1/255, not 0 — a window at opacity 0 stops receiving the mouse
  and the drag would stop.
- The window shows the image it had when grabbed for the whole drag.

## 4. Safety and timing rules

- Never on a game (Game Mode classification + detected library folders), on a fullscreen
  window, on Prism's own windows, on owned/tool windows, on windows smaller than
  200×120, or while Game Mode is active.
- The overlay is click-through and never takes focus.
- **A late effect is worse than none**: an event older than 250 ms is skipped.
- An effect Prism triggered itself (bar click) is not animated again when Windows
  reports the same transition.
- The window is copied *before* the transition, so copying never delays the effect:
  when it gets focus, and again when the mouse button goes down on its bar button.
  A minimized window is never copied (Windows parks it off-screen as a 160×28 stub).
- Every window hidden for an effect is journaled (`fx-hidden.json`: window, process,
  original style). A bar killed during an effect makes those windows visible again at
  its next start; same window **and** same process, otherwise nothing is touched.
- Diagnostics: an empty `fx-debug.log` in Prism's data folder makes the bar log the
  events it receives and its decisions, and write a few displayed drag frames as PPM.
- Every animation is measured (latency to first frame, time per frame, dropped frames)
  into `%ProgramData%\Prism\fx-stats.json` (last 50); `prism fx stats` prints them and
  `prism fx demo` plays a measured sequence on the foreground window.

## 5. Measurements

Frame computation alone, release build, one core of the build server, 1280×720 window on
a 1920×1080 overlay (`cargo test --release -p prism-core fx_bench -- --ignored --nocapture`):

| Effect | Average | Worst |
|---|---|---|
| Genie | 1.4 ms | 4.5 ms |
| Jelly | 2.4 ms | 5.3 ms |
| Zoom | 2.3 ms | 3.1 ms |

On Windows (VM, software rendering): latency to first frame 2–6 ms, 1.4–2 ms per frame,
0 dropped frames; jelly while dragging 2.2–2.9 ms per frame, 0 dropped frames over 5
drags; maximize/snap 2.2–5.2 ms latency, 1.3–2.7 ms per frame, 0 dropped frames.

New effects, computation alone on the build server (1280×720 window): Squash 0.4 ms,
3D tilt 0.9 ms, Fade 1.7 ms, Fall apart 2.0 ms per frame on average. Details and the bugs these measurements found:
`docs/measurements.md` §6.

## 6. Not done yet

- **Live content while dragging** (a video keeps playing): would need a capture every
  frame (33–49 ms each in the VM), too slow without Windows.Graphics.Capture.
- **Fresh copy for a minimize started by the window itself**: Windows has already
  minimized it when the event arrives, so the copy from its last focus is used.
- **Maximize/snap from a stale copy**: if the window's content changed since its last
  copy (taken when it got focus), the first frames show the older content, scaled; the
  real window fades in from mid-course.
- **Open effect** depends on how fast the new window draws its first content: it is
  played on whatever the window shows when it appears.
- Validation on physical hardware (integrated GPU, high refresh rates).
